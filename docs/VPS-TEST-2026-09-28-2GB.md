## How much memory `next build` needs

Measured outside musdash, in a plain `node:24-bookworm-slim` container on the
same host with the same source, reading the container's cgroup:

| Build                  | Cap      | Result                                   | Peak anon |
| ---------------------- | -------- | ---------------------------------------- | --------- |
| `next build`           | 1400 MiB | done, 43s                                | 1254 MiB  |
| `next build`           | 900 MiB  | no progress in 240s, killed by `timeout` | 838 MiB   |
| `next build --webpack` | 900 MiB  | done, 177s                               | 408 MiB   |

Turbopack does not scale down to the memory it is given: it needs about
1.25 GiB for an empty app and stalls below that. Webpack fits in under half
of BuildKit's cap on its own, but inside BuildKit it held 860–890 MiB for its
3.5 minutes. The build worked with little room to spare.

## Important

### T-1. A fix pushed within a minute of a failed push is dropped

`mus-docker`: the broken push arrived at 14:43:10 and failed at 14:43:21. The
fix arrived at 14:43:52, in the same 60-second bucket, and was logged as
`push coalesced into a deploy already queued this minute` — but that deploy
had already finished. The fix never deployed, and nothing in the dashboard
said so. `src/jobs/deploy.ts:780-799` documents this as an accepted trade-off
(`PUSH_BUCKET_MS`), but a failed build followed by a quick fix is the most
common flow in which it happens, and the log line is untrue in exactly that
case.

### T-2. Railpack builds never reuse their own layers

Two builds of the same `mus-node` commit, 90s apart with no BuildKit restart
in between: every step on the Railpack builder image ran again —
`install mise packages: node` (10.5s), `install apt packages: libatomic1`
(11.4s), `npm install`, `npm run build`. Only the steps on the runtime image
were `CACHED`. BuildKit held 2.56 GB of cache and its GC ceiling is 10 GB, so
nothing was evicted; something in the build's inputs changes every time. The
same miss made the `saas-template` redeploy re-run `npm install` (40s) and
`next build` (55s) for an unchanged commit. The cause is not yet known.

### T-3. A stock Next.js 16 app cannot build on 2GB, and takes 11.5 minutes to say so

See the table above: Turbopack needs about 1.25 GiB and BuildKit has 960 MiB.
Without host swap the kernel never kills the step, so the only thing that
ends the build is the 10-minute stall check. The failure is safe and the
message is right, but the advice ("build elsewhere, or use more memory")
misses the one-line fix that worked on this same host: build with webpack.
