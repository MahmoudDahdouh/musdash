## Critical

### C-1. A resource's first deploy is unreachable — the dashboard catch-all swallows it

**Invariant / criterion:** DoD step 8; the product's core promise that a deploy
is reachable at its URL.

**Observed.** After the first deploy of `web`, `https://web.168.235.65.93.sslip.io/`
returned `303 → /login` (the musdash dashboard) instead of nginx. Caddy's route
list was:

```
0  musdash-dashboard                  (no host matcher, terminal)
1  musdash-01M3BW7SYSQ91XGZ2PAGQAQNKJ (host: web.168.235.65.93.sslip.io)
```

Routes are evaluated in order and every musdash route is `terminal`, so the
host-less dashboard route matches everything and route 1 is never reached.

**Cause.**

- `src/jobs/deploy.ts:221` switches traffic with `caddy.upsertRoute`, which
  for a new id POSTs to `/config/apps/http/servers/srv0/routes/` — an
  **append** (`src/caddy/client.ts:218-230`).
- The comment at `src/caddy/client.ts:352-356` names exactly this hazard and
  relies on `ensureDashboardRoutes` re-appending the dashboard routes last.
- That only runs from `ensureCaddy()` (`src/caddy/bootstrap.ts:177`) and the
  dashboard-host job (`src/jobs/dashboard.ts:33`). The reconciler queues
  `ensureCaddy` only when Caddy is **not running** or its admin API does not
  answer (`src/reconciler.ts:230-247`). On a healthy host nothing ever fixes
  the order.

**Consequence.** Every newly created resource is unreachable after its first
deploy, indefinitely, on every install. Redeploys PATCH in place and keep the
position, so the route stays broken. Restarting musdash does not fix it,
because Caddy is still running.

**Workaround used to continue testing.** Saving a hostname under Settings →
Dashboard address runs `ensureDashboardRoutes`, which moves both dashboard
routes to the end. After that the app served `200` from nginx.

**Not yet reproduced:** a second resource created after the workaround.
From the code it will be appended behind the catch-all again.

### C-2. Every deployed app can rewrite the Caddy configuration

**Invariant:** "The Caddy admin API is never published to the host" and "treat
any path that can influence a container spec as a privilege boundary"
(CLAUDE.md, Security constraints).

**Observed.** From inside the user's nginx container:

```
wget -qO- http://musdash-caddy:2019/config/apps/http/servers/srv0/routes
→ full route list, including the dashboard's upstream
```

Only a read was tested. The same unauthenticated API accepts `POST`, `PATCH`,
`DELETE` and `/load`.

**Cause.** `src/caddy/bootstrap.ts:107` sets `CADDY_ADMIN=0.0.0.0:2019` so the
loopback port mapping (`bootstrap.ts:134-139`) can reach it. `0.0.0.0` inside
the container also means every interface on the `musdash` network, which is
the network every user app is attached to. Caddy logs this itself: `admin
endpoint on open interface; host checking disabled`. The host-side protection
holds (`127.0.0.1:2019` on the host; unreachable from the internet, verified).
The container-network side does not.

**Consequence.** Any app a user deploys — including a compromised dependency
or a one-click template — can redirect the dashboard's hostname to itself and
capture the admin login, hijack other apps' domains, or take down all routing.
This crosses the boundary between untrusted workload and control plane.

### C-3. The host does not survive a reboot at 512MB (DoD step 12)

**Criterion:** DoD step 12, and the frugality claim itself — 512MB is the
smallest box anyone would choose _because_ of that claim.

**Observed, before the reboot.** With nothing but the Phase 1 stack running
(Docker, Caddy, BuildKit, musdash, one nginx), Ubuntu's daily
`apt.systemd.daily` / `unattended-upgrade --download-only` started. The host
went into memory thrash:

- `%Cpu: 92.3 sy`, `kswapd0` at 25%, load average 5.7 on 1 vCPU
- 7MB free, ~95MB available, no swap
- `docker ps` hung for more than 4 minutes; `unattended-upgrade` stuck in `D`
- the app timed out (`curl` exit 28) from ~09:09 UTC onward

**Observed, after the reboot.** The host booted at ~09:14 UTC. The app never
answered again. It timed out on every request for the 20+ minutes it was
measured. SSH answered exactly once, at 09:28, then went back to connection
and banner-exchange timeouts. The host needed a power cycle from the
provider's console.

**Probable cause (unconfirmed).** Boot restarts the whole stack while apt's
missed daily timers (`Persistent=true`) fire at the same moment, on a box with
no swap. Without swap, the kernel can only reclaim file-backed pages, so it
evicts and re-reads executables in a loop. The previous boot's journal has
not been read yet; that is what confirms or refutes this.

**Consequence.** On the target hardware, as installed today, musdash is not
self-healing across a reboot — the host itself stops responding. Nothing in
`install.sh` or `docs/RUNNING.md` sets up swap or states a minimum host size.

## Important

### I-1. One request fails at every route switch — zero-downtime is not zero

**Invariant:** "The old container is never stopped until the new one passes the
health gate and the Caddy route has been switched" — the zero-downtime
guarantee (DoD steps 9, 10).

**Observed.**

| Run                                           | Requests | Failed                                        | Failure                                 |
| --------------------------------------------- | -------- | --------------------------------------------- | --------------------------------------- |
| Quiet baseline, no deploy                     | 200      | 0                                             | —                                       |
| Redeploy `nginx:alpine` → `nginx:1.27-alpine` | 229      | 1 at the switch (+1 unexplained, 20s earlier) | `000`                                   |
| Rollback                                      | 121      | 1 at the switch                               | `000`, curl exit 35 (TLS connect error) |

The rollback failure lined up with Caddy's log to the millisecond: the `PATCH
/id/musdash-<resource>` at 09:02:11.63 UTC was followed by `admin endpoint
started`, `servers shutting down with eternal grace period`, and a fresh `server
running`. That is a **full config reload**. A TLS handshake that arrived inside
that window failed. The old container was still running throughout; ordering
was correct. The switch mechanism itself drops the request.

**Where.** `src/jobs/deploy.ts:221` → `caddy.upsertRoute` → `PATCH /id/<id>`
(`src/caddy/client.ts:218-224`). The comment there says the PATCH "swaps the
upstream atomically … no request sees a half-updated route". The route is
atomic. The listener restart around it is not.

### I-2. The dashboard port is open to the internet on a stock Ubuntu image

**Invariant:** D23 — "the firewall is the boundary".

**Observed.** `ufw` is installed but inactive on RamNode's Ubuntu 24.04 image.
`install.sh` adds its allow/deny rules (`scripts/install.sh:269-279`) and
prints `ufw is installed but inactive — port 8000 is reachable from anywhere`,
but does not enable it. `http://168.235.65.93:8000/health` answered `200` from
the public internet. The whole design depends on a firewall that, on this
provider, is off by default.

### I-3. Installing on 512MB succeeds by a thin margin

**Observed** (memory sampled every 2s during install):

| Moment                                               | Available |
| ---------------------------------------------------- | --------- |
| Fresh box                                            | 296MB     |
| `fwupd` spawned by the Docker install (188MB RSS)    | **43MB**  |
| `bun run build` compiling musdash (Bun at 163MB RSS) | **48MB**  |
| After install, idle                                  | 181MB     |

Both dips came within ~45MB of an OOM kill. `install.sh` hides the build's
output (`>/dev/null`, `scripts/install.sh:176-177`). If the compile is
OOM-killed, all the operator sees is `set -e` exiting with no message.

## Minor

### M-1. Invalid `pattern` on the project name field

`src/views/pages/projects.eta:45` — `pattern="[A-Za-z0-9 _-]{1,60}"`. Browsers
compile `pattern` with the `v` flag, where an unescaped `-` in a class is a
syntax error. The console logs `Invalid regular expression … Invalid character
in character class`, and the browser silently skips the validation. It should
be `[A-Za-z0-9 _\-]{1,60}`. Check other templates for the same construction.

### M-2. `request failed` logs do not say which request

`src/index.ts:33` logs `{ code, err }` only. The journal filled with
`NOT_FOUND request failed` at level `error`, with no method or path, so none
of them could be traced. A 404 is also arguably not `error` level.

### M-3. Settings shows the success message twice

After saving a dashboard address, the page shows both the flash banner (from
`src/routes/app.ts:781`) and the inline note from
`src/views/pages/settings.eta:44`, saying the same thing.

### M-4. Idle RSS passes; peak RSS during deploys is over the ceiling

`/proc/<pid>/status` after the tests: `VmRSS 40.7MB`, `VmHWM 104.5MB`. The
100MB gate measures idle only, as specified. But on a 512MB host a deploy
briefly holds more than the whole budget, and that contributes to C-3. Worth
recording whether a peak figure should be reported next to the idle one.

### M-5. `CLAUDE.md` describes a different project

It still says the repository is a scaffold, that `src/index.ts` is a hello-world
server, that `bun test` has "no tests exist yet", and that the dev machine is

macOS. Future sessions start from the wrong picture.

## Important

### N-1. BuildKit's API is reachable by every deployed app — the C-2 hole, on the other sidecar

**Invariant:** "Docker socket access is root-equivalent … treat any path that
can influence a container spec as a privilege boundary". Also the rule this
commit added to CLAUDE.md, that it "applies to any unauthenticated sidecar API".

`src/build/bootstrap.ts:210-212` starts `buildkitd` with
`--addr tcp://0.0.0.0:1234`. The container runs with `privileged: true`
(`:185`) and is attached to `config.network` (`:165`), the network every user
app is on. The `0.0.0.0` is there for the same reason Caddy's admin API used to
be: so the host's loopback port mapping can reach it (comment at `:192-198`).
The result is also the same. Any app can reach `musdash-buildkit:1234`
unauthenticated, and can:

- run arbitrary builds on the host's CPU and RAM — on a 512MB host that is C-3
  on demand
- fill or prune the build cache
- probe a privileged daemon's attack surface

`docs/RUNNING.md:343` still says BuildKit "is loopback-only by design". That is
false on the running system.

This predates `a619984`. It should still be fixed before the VPS re-run.
Otherwise the re-run proves C-2 closed on one sidecar while the identical hole
stays open on the other.

### N-2. Replacing an outdated proxy can leave the host with no proxy at all

**Invariant:** the zero-downtime guarantee, and `docs/RUNNING.md` ("nothing
leaves the host without a proxy").

`src/caddy/bootstrap.ts:153-171` force-removes the outdated Caddy container
first (`:170`), then creates and starts the replacement. If the Engine rejects
the new spec, nothing holds `:80`/`:443` and every site on the host is down.
Possible causes include:

- the new `Sysctls` entry
- the bind-mount source
- a stale image cache

Recovery is the reconciler re-queueing the same bootstrap every 5 minutes with
`maxAttempts: 1`. That repeats the same deterministic failure, so the outage
lasts until an operator steps in.

A failure at start is worse than one at create. The new container already
carries `musdash.proxy_spec=2`, so every later `ensureCaddy` adopts it and
never recreates it.

D29 accepts "no rollback". But a create-time rejection is detectable _before_
the old proxy is removed, and the code does not check for one.

Must be exercised on the VPS by upgrading a gen-1 install and timing the outage.

### N-3. A resource can take over the dashboard's hostname

**Invariant:** C-2's goal — nothing a resource does may capture the dashboard
login.

`POST /settings/dashboard-host` refuses a hostname already attached to a
resource. The reverse check is missing:

- `POST /r/:resourceId/domains` (`src/routes/app.ts:584-600`) checks only
  `domainExists(host)`.
- The auto-domain added when a resource is created checks nothing either.

Since C-1, resource routes always sit ahead of both dashboard routes. So
attaching the dashboard's hostname to a resource sends that name, and the
login typed through it, to the app from the next deploy or the next
`syncResourceRoutes` onward.

The bare-IP catch-all still reaches the dashboard, so this is operator
self-harm rather than an external attack. It is still one typo away.

### N-4. The I-1 fix is unproven, and absent on older kernels

**Invariant:** the zero-downtime guarantee (DoD steps 9, 10).

The proxy sets `net.ipv4.tcp_migrate_req`. It is correctly a per-namespace
sysctl that Docker permits, applied to Caddy's `:80`/`:443` listeners. Four
things remain unproven:

1. Migration only helps if Caddy binds its new `SO_REUSEPORT` listener
   _before_ closing the old one. The Caddy log order recorded in I-1 does not
   settle which happens first.
2. It rescues connections sitting in the closing listener's accept queue. That
   fits the curl exit 35 in I-1. It does nothing for a connection Go had
   already accepted that is mid TLS handshake when the server shuts down.
3. It is TCP only. HTTP/3 on `443/udp` is untouched, and the probe was TCP only.
4. The second, unexplained failure 20s before the redeploy switch is not
   addressed.

On kernels older than 5.14 (Ubuntu 20.04 GA, Debian 11), the proxy is created
without the sysctl (`src/caddy/bootstrap.ts:311`). The only sign is a log
line, and the product still claims zero downtime.

Only a re-run of DoD steps 9–10 with the same probe can close I-1.

### V-1. BuildKit's memory cap is larger than a 1GB host (Important)

**Invariant:** "Every container musdash creates has a hard memory limit … a
leaking user app must never take down the box or the dashboard."

`src/build/bootstrap.ts:50` fixes `BUILDKIT_MEMORY_BYTES` at 1GiB. On this

## V-1 premise test (before the fix)

A separate session on the same 1GB host, run to check V-1's fix before it was
built: does a memory cap on the `musdash-buildkit` container actually contain a
build step, or do build steps escape it? Cgroup v2, Ubuntu 24.04, kernel
6.8.0-51, with the code as tested above (BuildKit created with its fixed 1 GiB).

**Idle baseline**, 2026-09-25 16:54 UTC, with `web` and `web2` deployed:

| Reading                                          | Value                       |
| ------------------------------------------------ | --------------------------- |
| `free -m` available (three readings)             | 510, 535, 536 MiB           |
| musdash                                          | 63 MiB                      |
| Caddy                                            | 67 MiB                      |
| BuildKit (its container cgroup `memory.current`) | 66–69 MiB                   |
| The two nginx apps together                      | ~14 MiB                     |
| OS + dockerd + containerd, derived               | ≈ 961 − 535 − 210 ≈ 216 MiB |

**Method.** The running daemon was capped by hand with
`docker update --memory 384m --memory-swap 384m musdash-buildkit`, and this was
built through `buildctl` against `/opt/musdash/data/buildkit/buildkitd.sock`:

```dockerfile
FROM python:3.12-alpine
RUN python3 -c "import time; c=[]; [(c.append(bytearray(50*1024*1024)), print((i+1)*50, flush=True), time.sleep(1)) for i in range(14)]"
```

The cap was restored to `1073741824` afterwards.

**Observed:**

- The step printed 50 … 300 MiB one per second, then 350 at 12.0 s (reclaim
  pressure inside the cgroup), then died; `buildctl` exited 1.
- The container cgroup's `memory.current`, sampled every second, climbed
  166 → 269 → 346 → 383 → 384 MiB, then fell to 82 MiB after the kill.
- `memory.events`: `max 6467`, `oom 1`, `oom_kill 1`.
- Kernel: `oom-kill:constraint=CONSTRAINT_MEMCG … oom_memcg=/system.slice/docker-<buildkit id>.scope`
  and `Memory cgroup out of memory: Killed process 2921 (python3) … anon-rss:370172kB`.
  Not a global "Out of memory".
- Host `available` went 528 → 418 → 318 → 218 → 166 MiB and recovered to 507;
  load average stayed at or below 0.64.
- Afterwards musdash's `/health` answered 200 and the nginx app 200 over HTTPS.
  The BuildKit container stayed up: only the step's process was killed.

**Conclusion.** Build steps are charged to the buildkitd container's cgroup on
cgroup v2, so a cap below the host's memory contains a runaway build to the
build step. V-1's fix (D33) rests on this. Not verified on cgroup v1.

## New findings

### R-1. A restart within the bootstrap job's time bucket skips the bootstrap (Important)

`src/reconciler.ts` gives the boot-time `ensure_buildkit` and `ensure_caddy`
jobs the same time-bucketed id as the reconciler's self-heal (1 minute for
BuildKit, 5 for Caddy). The queue keeps finished rows until the daily prune,
so if musdash restarts in the same bucket as its previous boot, the id
collides with the completed row and the bootstrap never runs. Seen here:
setting `MUSDASH_BUILDKIT_MEMORY_MB=512` and restarting within the minute of
the previous restart changed nothing and logged nothing; the same restart in a
new minute replaced the daemon. For Caddy the window is five minutes, so an
upgrade that lands within five minutes of the previous boot (a re-run of the
installer, a quick fix-and-restart) does not re-ensure the proxy.

### R-2. A deterministic build failure is retried three times (Minor)

The runaway build failed at 20:56:34, 20:56:52 and 20:58:00 — three attempts
of the same deployment, each running the build to BuildKit's cap again. A
build step that fails the same way every time costs three builds and holds the
single worker for them; the third ran just before the next queued deploy.

### R-3. `measure-rss.ts` boots the binary with the caller's environment (Minor)

`bun run gate:rss` spawns `dist/musdash` with the inherited environment: port
8000, `./data` and the real Docker socket. On CI that is harmless. On a real
host it starts a second musdash with an empty database whose reconciler
removes every app container as an orphan — which is what happened during this
pass when the binary was run by hand with an unknown flag (the live reconciler
redeployed both apps within ~25 s). The gate should run on its own port, a
temporary data directory and no Docker socket. Its closing line also still
quotes "Caddy ~50MB, BuildKit idle ~12MB" (measured 67 and 66).

### R-4. The installer's closing banner says "create your admin account" on an upgrade (Minor)

After upgrading an install that already has its account, the box still reads
"Open http://… to create your admin account."

### R-5. Saving variables with empty boxes deletes the saved ones (UX, Minor)

Saved values are never shown again, so the three boxes on a resource's
Variables tab are empty even when the resource has variables (here `web` has
`FOO`, listed only in the Resolved environment table above). Saving replaces
all three boxes, so adding one variable deletes every existing one. The
confirmation dialog says so, but the empty boxes invite exactly that mistake.
