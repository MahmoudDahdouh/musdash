## Critical

### C-1. A resource's first deploy is unreachable — the dashboard catch-all swallows it

**Invariant / criterion:** DoD step 8; the product's core promise that a deploy
is reachable at its URL.

**Observed.** After the first deploy of `web`, `https://web.168.235.65.93.sslip.io/`
returned `303 → /login` (the musdash dashboard) instead of nginx. Caddy's route
list was:

```
0  musdash-dashboard                  (no host matcher, terminal)
1  musdash-01M3BW7SYSQ91XGZ2PAGQAQNKJ (host: web.168.235.65.93.sslip.io)
```

Routes are evaluated in order and every musdash route is `terminal`, so the
host-less dashboard route matches everything and route 1 is never reached.

**Cause.**

- `src/jobs/deploy.ts:221` switches traffic with `caddy.upsertRoute`, which
  for a new id POSTs to `/config/apps/http/servers/srv0/routes/` — an
  **append** (`src/caddy/client.ts:218-230`).
- The comment at `src/caddy/client.ts:352-356` names exactly this hazard and
  relies on `ensureDashboardRoutes` re-appending the dashboard routes last.
- That only runs from `ensureCaddy()` (`src/caddy/bootstrap.ts:177`) and the
  dashboard-host job (`src/jobs/dashboard.ts:33`). The reconciler queues
  `ensureCaddy` only when Caddy is **not running** or its admin API does not
  answer (`src/reconciler.ts:230-247`). On a healthy host nothing ever fixes
  the order.

**Consequence.** Every newly created resource is unreachable after its first
deploy, indefinitely, on every install. Redeploys PATCH in place and keep the
position, so the route stays broken. Restarting musdash does not fix it,
because Caddy is still running.

**Workaround used to continue testing.** Saving a hostname under Settings →
Dashboard address runs `ensureDashboardRoutes`, which moves both dashboard
routes to the end. After that the app served `200` from nginx.

**Not yet reproduced:** a second resource created after the workaround.
From the code it will be appended behind the catch-all again.

### C-2. Every deployed app can rewrite the Caddy configuration

**Invariant:** "The Caddy admin API is never published to the host" and "treat
any path that can influence a container spec as a privilege boundary"
(CLAUDE.md, Security constraints).

**Observed.** From inside the user's nginx container:

```
wget -qO- http://musdash-caddy:2019/config/apps/http/servers/srv0/routes
→ full route list, including the dashboard's upstream
```

Only a read was tested. The same unauthenticated API accepts `POST`, `PATCH`,
`DELETE` and `/load`.

**Cause.** `src/caddy/bootstrap.ts:107` sets `CADDY_ADMIN=0.0.0.0:2019` so the
loopback port mapping (`bootstrap.ts:134-139`) can reach it. `0.0.0.0` inside
the container also means every interface on the `musdash` network, which is
the network every user app is attached to. Caddy logs this itself: `admin
endpoint on open interface; host checking disabled`. The host-side protection
holds (`127.0.0.1:2019` on the host; unreachable from the internet, verified).
The container-network side does not.

**Consequence.** Any app a user deploys — including a compromised dependency
or a one-click template — can redirect the dashboard's hostname to itself and
capture the admin login, hijack other apps' domains, or take down all routing.
This crosses the boundary between untrusted workload and control plane.

### C-3. The host does not survive a reboot at 512MB (DoD step 12)

**Criterion:** DoD step 12, and the frugality claim itself — 512MB is the
smallest box anyone would choose _because_ of that claim.

**Observed, before the reboot.** With nothing but the Phase 1 stack running
(Docker, Caddy, BuildKit, musdash, one nginx), Ubuntu's daily
`apt.systemd.daily` / `unattended-upgrade --download-only` started. The host
went into memory thrash:

- `%Cpu: 92.3 sy`, `kswapd0` at 25%, load average 5.7 on 1 vCPU
- 7MB free, ~95MB available, no swap
- `docker ps` hung for more than 4 minutes; `unattended-upgrade` stuck in `D`
- the app timed out (`curl` exit 28) from ~09:09 UTC onward

**Observed, after the reboot.** The host booted at ~09:14 UTC. The app never
answered again. It timed out on every request for the 20+ minutes it was
measured. SSH answered exactly once, at 09:28, then went back to connection
and banner-exchange timeouts. The host needed a power cycle from the
provider's console.

**Probable cause (unconfirmed).** Boot restarts the whole stack while apt's
missed daily timers (`Persistent=true`) fire at the same moment, on a box with
no swap. Without swap, the kernel can only reclaim file-backed pages, so it
evicts and re-reads executables in a loop. The previous boot's journal has
not been read yet; that is what confirms or refutes this.

**Consequence.** On the target hardware, as installed today, musdash is not
self-healing across a reboot — the host itself stops responding. Nothing in
`install.sh` or `docs/RUNNING.md` sets up swap or states a minimum host size.

## Important

### I-1. One request fails at every route switch — zero-downtime is not zero

**Invariant:** "The old container is never stopped until the new one passes the
health gate and the Caddy route has been switched" — the zero-downtime
guarantee (DoD steps 9, 10).

**Observed.**

| Run                                           | Requests | Failed                                        | Failure                                 |
| --------------------------------------------- | -------- | --------------------------------------------- | --------------------------------------- |
| Quiet baseline, no deploy                     | 200      | 0                                             | —                                       |
| Redeploy `nginx:alpine` → `nginx:1.27-alpine` | 229      | 1 at the switch (+1 unexplained, 20s earlier) | `000`                                   |
| Rollback                                      | 121      | 1 at the switch                               | `000`, curl exit 35 (TLS connect error) |

The rollback failure lined up with Caddy's log to the millisecond: the `PATCH
/id/musdash-<resource>` at 09:02:11.63 UTC was followed by `admin endpoint
started`, `servers shutting down with eternal grace period`, and a fresh `server
running`. That is a **full config reload**. A TLS handshake that arrived inside
that window failed. The old container was still running throughout; ordering
was correct. The switch mechanism itself drops the request.

**Where.** `src/jobs/deploy.ts:221` → `caddy.upsertRoute` → `PATCH /id/<id>`
(`src/caddy/client.ts:218-224`). The comment there says the PATCH "swaps the
upstream atomically … no request sees a half-updated route". The route is
atomic. The listener restart around it is not.

### I-2. The dashboard port is open to the internet on a stock Ubuntu image

**Invariant:** D23 — "the firewall is the boundary".

**Observed.** `ufw` is installed but inactive on RamNode's Ubuntu 24.04 image.
`install.sh` adds its allow/deny rules (`scripts/install.sh:269-279`) and
prints `ufw is installed but inactive — port 8000 is reachable from anywhere`,
but does not enable it. `http://168.235.65.93:8000/health` answered `200` from
the public internet. The whole design depends on a firewall that, on this
provider, is off by default.

### I-3. Installing on 512MB succeeds by a thin margin

**Observed** (memory sampled every 2s during install):

| Moment                                               | Available |
| ---------------------------------------------------- | --------- |
| Fresh box                                            | 296MB     |
| `fwupd` spawned by the Docker install (188MB RSS)    | **43MB**  |
| `bun run build` compiling musdash (Bun at 163MB RSS) | **48MB**  |
| After install, idle                                  | 181MB     |

Both dips came within ~45MB of an OOM kill. `install.sh` hides the build's
output (`>/dev/null`, `scripts/install.sh:176-177`). If the compile is
OOM-killed, all the operator sees is `set -e` exiting with no message.

## Minor

### M-1. Invalid `pattern` on the project name field

`src/views/pages/projects.eta:45` — `pattern="[A-Za-z0-9 _-]{1,60}"`. Browsers
compile `pattern` with the `v` flag, where an unescaped `-` in a class is a
syntax error. The console logs `Invalid regular expression … Invalid character
in character class`, and the browser silently skips the validation. It should
be `[A-Za-z0-9 _\-]{1,60}`. Check other templates for the same construction.

### M-2. `request failed` logs do not say which request

`src/index.ts:33` logs `{ code, err }` only. The journal filled with
`NOT_FOUND request failed` at level `error`, with no method or path, so none
of them could be traced. A 404 is also arguably not `error` level.

### M-3. Settings shows the success message twice

After saving a dashboard address, the page shows both the flash banner (from
`src/routes/app.ts:781`) and the inline note from
`src/views/pages/settings.eta:44`, saying the same thing.

### M-4. Idle RSS passes; peak RSS during deploys is over the ceiling

`/proc/<pid>/status` after the tests: `VmRSS 40.7MB`, `VmHWM 104.5MB`. The
100MB gate measures idle only, as specified. But on a 512MB host a deploy
briefly holds more than the whole budget, and that contributes to C-3. Worth
recording whether a peak figure should be reported next to the idle one.

### M-5. `CLAUDE.md` describes a different project

It still says the repository is a scaffold, that `src/index.ts` is a hello-world
server, that `bun test` has "no tests exist yet", and that the dev machine is
Windows. Phases 1–2 are built, 10 test files exist, and development is now on
macOS. Future sessions start from the wrong picture.
