## Important

### P-1. An interrupted job stays `leased` until a restart that happens after its lease expires

**Invariant:** the queue's own promise, `src/queue/worker.ts:27-28` — "This
single call is what makes an interrupted deploy resume rather than hang
forever."

**Observed.** The host rebooted at 13:25. The reconciler queued redeploys of
two resources at 13:26. `install.sh` restarted musdash at 13:28 and a config
change restarted it at 13:30, both mid-deploy. At 13:45 both jobs were still
`leased` with `leased_until` 13:41 and 13:42, and their deployment rows were
still `running` with no `finished_at`.

**Cause.** `recoverExpiredLeases()` runs once, at worker start
(`src/queue/worker.ts:29`), and only reclaims leases already past
`leased_until`. The lease is 15 minutes (`src/queue/index.ts:13`). A restart
within 15 minutes of the lease being taken finds it unexpired and skips it, and
nothing runs recovery again until the next restart.

**Consequence.** The common upgrade path — reboot, then run `install.sh`
within minutes — leaves deployments showing "running" indefinitely. The
resource's container was brought back separately, so traffic was fine; the
dashboard was not.

### P-2. A failed build records no commit, and names the previous image

**Criterion:** DoD 6.

**Observed.** A push that broke `mus-docker`'s Dockerfile produced a
deployment row with `commit_sha`, `commit_message` and `commit_author` all
null. The resource's deployment table shows `—` for all three, and the image
column shows `musdash/mus-docker:cnwx9smj` — the image of the previous
_successful_ deploy, which is still serving.

**Cause.** Commit metadata and the new image tag are written only after
`buildFromSource` returns (`src/jobs/deploy.ts:201-210`). A build failure throws
before that, although the commit was resolved and even logged earlier
(`src/jobs/build.ts:126`, "At commit …").

**Consequence.** The one deploy where the user most needs to know which commit
it was is the one that does not say, and its row points at an image that
works.

### P-3. The BuildKit daemon keeps ~230MiB after builds, which the next build then lacks

25MiB idle before the first build, 220–250MiB for at least 40 minutes after
the last. It is not cache: `buildkitd` itself had `RssAnon` 227MiB,
`RssFile` 4kB. With a 384MiB cap and `MemorySwap` equal to `Memory`, the next
build starts with ~150MiB. The first `saas-template` build (P-8) began in
exactly this state. CLAUDE.md quotes BuildKit idle at ~66MB. Restarting the
container returns it to 25–65MiB.

## Critical

### P-8. A stock Next.js app cannot be built on a 1GB host, and the only knob that helps takes the host down

**Invariant / criterion:** Phase 2's zero-config Railpack promise, and "a
leaking user app must never take down the box or the dashboard" (CLAUDE.md).

Under the host-sized cap, a build does not fail — it stalls indefinitely (see
P-9). Raising the cap, which the settings file and the boot warning both offer,
let `next build` push the host into thrash and took every app and the
dashboard offline. There is no setting on this host under which the app
deploys and the host stays up. `next build` at ~520MiB plus the daemon exceeds
what a 1GB host can give a build while running musdash, Caddy and apps.

**Consequence.** On the target hardware, the most common kind of app people
will point musdash at cannot be deployed from source. Nothing tells the user
that before, during, or after the attempt.

## Important (from the `saas-template` run)

### P-9. A build that is starved at the cap stalls for 30 minutes instead of failing

BuildKit's container has `MemorySwap` equal to `Memory`, so at the cap the
kernel reclaims file pages (binaries, npm's cache) over and over rather than
OOM-killing: 1.98M `max` events, zero `oom_kill`. The deploy log shows no new
line for the whole 30 minutes, then ends with `ERRO failed to solve: …
context canceled` and `railpack exited with code 1`. Nothing says "timed out"
or "out of memory". DECISIONS mentions turning exit 137 into an "out of
memory" line; a stall never produces a 137.

### P-10. A timed-out build keeps running inside BuildKit

After attempt 1 was marked failed at 14:41, `npm install` (pid 15484),
`apt-get install` and `dpkg-preconfigure` were still running in BuildKit's
step cgroups, holding the cap. The timeout ends the `railpack`/`buildctl`
client; the daemon's solve continues. The next build would have started into a
full cgroup. Only restarting the container cleared it.

The "Build only" and "Both" textareas are not exposed as text boxes, so a
screen reader or keyboard-only user cannot reliably reach them.

### P-7. The upgrade replaces Caddy once

Upgrading from `6aa76bf` replaced the proxy to apply its new 224MB cap (L-fix),
leaving a few seconds with no proxy. Expected once per host, but not mentioned
anywhere an operator would see before upgrading.

The resource's deployment table lists the three failed `saas-template`
deployments with image `(building)` and `—` for commit, message and author
(P-2). "Building" reads as still in progress.
