## `saas-template` with swap

The fix did what D50 set out to do for the host, and not for the app.

- `npm install` and Railpack's parallel `apt-get install` finished (29s),
  where on 2026-09-27 they stalled at the cap for 30 minutes. BuildKit filled
  its RAM (384 MiB) and then its swap allowance (383 MiB).
- `next build` ran "Creating an optimized production build" for 228s, then
  was killed: `#17 238.4 Killed … did not complete successfully: cannot
allocate memory`. The deploy failed at 4m10s, not 30 minutes.
- Lowest `MemAvailable` 198 MB, host swap peak 526 MB. The dashboard and all
  three apps answered throughout. BuildKit was restarted after the failure
  and idled at 25 MiB.

So the host is now safe from this build, and a stock Next.js app still cannot
be built on 1GB with a 384 MiB cap plus as much again in swap. The 10-minute
stall check never ran: with swap, the kernel killed the step first.

## Important

### R-1. After an upgrade the browser runs the old script against new pages for up to an hour

`/assets/alpine.js` (Alpine plus `app.js`) and `/assets/app.css` are served
with `cache-control: public, max-age=3600` at a fixed URL
(`src/views/render.ts:137-146`, `src/views/layout.eta:15`). After the upgrade
the dashboard served the new `project.eta` (with `x-ref="repoList"`) while the
browser kept the cached script with the old `visibleCount`, so P-4 still
showed "no match" beside the matches until the cache entry was refreshed by
hand. Any change that moves markup and script together breaks the same way
after an upgrade.

### R-2. A step killed for memory is still reported as "railpack exited with code 1"

The P-9 fix names a memory kill only when BuildKit prints `exit code: 137`
(`src/build/run.ts`, `MEMORY_KILL`). Under swap the kill surfaced as
`ERROR: process "npm run build" did not complete successfully: cannot allocate
memory` and `ResourceExhausted`, so the deploy's error, and the advice meant
for exactly this app, never appeared.

## Minor

### R-3. The reconciler queues BuildKit bootstraps while a build fills its memory

At 23:09:10, a minute into the `saas-template` build, the reconciler logged
`BuildKit is not running or not answering on its socket, queueing bootstrap`
— the daemon was too busy swapping to answer the 2s probe. Three
`ensure_buildkit` jobs ran after the deploy and each adopted the daemon.
Harmless, but it reads as a crash in the log.

### R-4. A rollback row has no commit

The rollback to `musdash/mus-node:63kewgq4` shows `—` for commit, message and
author, although the deployment that built that image recorded `19dd2fe`.

## Not covered by this run

- BuildKit's restart after a successful build that kept more than half its
  cap: no build here left more than 34 MiB.
- Disconnecting the GitHub App.
